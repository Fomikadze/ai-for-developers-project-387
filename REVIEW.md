# REVIEW.md

Правила для ревью кода, в том числе независимого авторевью (скилл `code-review`). Ревьюер читает этот файл целиком до того, как смотреть diff. Здесь собраны правила бронирования из спецификации. Источники правды — [docs/requirements.md](docs/requirements.md), [docs/schedule.md](docs/schedule.md), [docs/api.md](docs/api.md), [docs/architecture.md](docs/architecture.md), [docs/frontend.md](docs/frontend.md) и `typespec/main.tsp`. Если файл расходится с ними, верны они, а расхождение само по себе считается замечанием к `REVIEW.md`.

## Формат замечания

Каждое замечание содержит четыре поля. Замечание без любого из них не принимается: его нужно дополнить или снять.

| Поле | Что писать |
| --- | --- |
| **Файл** | путь от корня репозитория |
| **Строка** | номер строки или диапазон в новой версии файла (`path:42` или `path:42-48`) |
| **Условия ошибки** | конкретные входные данные или состояние, при которых код ведёт себя неправильно: запрос, время по `Clock`, существующие брони, порядок одновременных запросов |
| **Последствие** | что именно пойдёт не так: неверный код или статус ответа, двойная бронь, потерянные данные формы, неверный слот, падение |

Ещё два правила:

- Ссылайся на нарушенное правило: номер из списка ниже или файл и раздел `docs/`.
- «Может быть, стоит…» без условий и последствия — не замечание. Стиль, который ловят линтеры, не обсуждаем.

Пример:

```text
Файл: backend/infrastructure/src/main/kotlin/.../InMemoryBookingRepository.kt
Строка: 31-37
Правило: Б1 (атомарность)
Условия ошибки: два POST /api/bookings на один start приходят одновременно; оба проходят проверку пересечения до вставки
Последствие: обе брони сохраняются, 201 обоим гостям, одно время занято дважды
```

## Правила бронирования

### Пересечения

- **Б1.** Проверка пересечения и вставка брони выполняются атомарно в одной критической секции под `Mutex` в `BookingRepository`. Любая проверка вне этой секции — ошибка, даже если тесты зелёные.
- **Б2.** Брони и слоты — полуинтервалы `[start, end)` в `Instant`. Интервалы пересекаются, если `a.start < b.end && b.start < a.end`. Встреча может начинаться в момент окончания предыдущей: стык не пересечение.
- **Б3.** Пересечение проверяется со всеми бронями всех типов встреч, а не только того же типа. Пересечение — `409 SLOT_TAKEN`.

### Слоты и окно записи

- **Б4.** Часовой пояс владельца — `Asia/Almaty`. Рабочие часы — понедельник–пятница 09:00–18:00, праздников и перерывов нет. Время в API — UTC с `Z`.
- **Б5.** Старты слотов идут с шагом 30 минут от 09:00, шаг общий для всех типов. Длительность слота равна длительности типа (15–540 минут) и не обязана быть кратной шагу. Слот целиком помещается в рабочий день: конец не позже 18:00.
- **Б6.** Окно записи — 14 календарных дней с завтра по завтра + 13 по `Asia/Almaty`. Выходные внутри окна занимают дни, но слотов не дают.
- **Б7.** Текущее время берётся только из внедрённого `Clock`. Прямой `Instant.now()`, `Clock.systemUTC()` или `LocalDate.now()` в логике слотов и броней — ошибка.
- **Б8.** `GET /api/meeting-types/{id}/slots` отдаёт только свободные слоты на всё окно, по возрастанию `start`. Занятые слоты гостю не показываются.

### Создание брони (`POST /api/bookings`)

- **Б9.** `start` принимается, только если совпадает со стартом слота по правилам Б4–Б6 без учёта занятости. Иначе `400 SLOT_OUT_OF_RANGE`.
- **Б10.** `end` вычисляет сервер как `start + durationMinutes`. Значение от клиента не используется.
- **Б11.** Проверки идут строго по порядку [docs/api.md](docs/api.md#порядок-проверок), возвращается первая ошибка:
  1. поля формы в порядке `guestName` → `guestEmail` → `guestPhone` → `notes`, затем `meetingTypeId` и `start` (`400`);
  2. тип встречи существует, не-UUID считается несуществующим (`404 MEETING_TYPE_NOT_FOUND`);
  3. `start` совпадает со слотом (`400 SLOT_OUT_OF_RANGE`);
  4. нет пересечения под `Mutex` (`409 SLOT_TAKEN`).
- **Б12.** Данные гостя проверяются паттернами из `typespec/main.tsp`, одинаковыми в контракте, Kotlin и zod-схеме фронтенда. Сервер не обрезает пробелы: `" Иван"` → `400 INVALID_NAME`. Телефон — E.164 `^\+[1-9]\d{6,14}$`.
- **Б13.** Поле `notes` (в интерфейсе — «Тема разговора», спека #6) необязательное, до 500 символов. Пустая строка равна отсутствию. В ответе ключ `notes` есть всегда: строка или `null`. Длиннее 500 — `400 VALIDATION_ERROR`. Имя поля в API и в коде не меняется.
- **Б14.** Ответ `201` — полная бронь: `id`, `meetingType { id, title }`, `start`, `end`, `guestName`, `guestEmail`, `guestPhone`, `notes`.

### Список предстоящих встреч

- **Б15.** `GET /api/bookings/upcoming` возвращает брони всех типов с `end > now` по `Clock` (идущая встреча тоже предстоящая), по возрастанию `start`.
- **Б16.** В карточке брони у владельца тема разговора выводится с подписью через ключ локали и только если `notes` не `null`. Пустой подписи без текста нет.

### Ошибки и фронтенд

- **Б17.** Ошибка API — `{ code, message }`, один код на ответ. Код есть в таблице [docs/api.md](docs/api.md#ошибки), в `ErrorCode` контракта и в обоих `frontend/src/locales/{ru,en}.json`. Бэкенд тексты не локализует.
- **Б18.** После `409 SLOT_TAKEN` фронтенд показывает «Это время уже заняли, выберите другое», перезапрашивает слоты и возвращает гостя к выбору времени. Тип встречи и данные формы, включая тему разговора, сохраняются.
- **Б19.** Фронтенд обращается к API только через сгенерированный SDK и группирует слоты по дням в часовом поясе из `GET /api/owner`.

### Вне рамок

- **Б20.** Отмена и перенос броней, редактирование и удаление типов встреч, показ занятых слотов, авторизация. Код для них без явной задачи — замечание (scope creep).

## Тесты

- **Т1.** Изменение правил Б1–Б16 сопровождается тестом на `testApplication` или юнит-тестом домена. Для Б1 нужен конкурентный тест: одновременные запросы на один слот дают ровно один `201`.
- **Т2.** Тесты окна записи и предстоящих встреч используют фиксированный `Clock`.
- **Т3.** Фронтенд-тесты ищут элементы по роли или подписи и проверяют видимый текст, а не внутреннее состояние.
